学索引的时候，教材第一页就写「B+ 树是有序的」，然后就跳到插入删除。但有个问题一直卡着我：**为什么索引非得是有序的？** 哈希表查找也是 O(1)，为什么不用它？

这篇是把这个问题想通之后的整理。结论先放在这里：有序不是为了「找得快」，而是为了*让「范围」和「排序」这两个动作不用额外付钱*。

> **一句话版本：** 哈希能定位一个点，只有有序结构才能一次定位一段。

## 先算一个数字：扇出

假设一个索引页 16 KB，主键是 8 字节的 bigint，页内指针 6 字节，那么一个页能放 `16384 / (8 + 6) ≈ 1170` 条目录项。三层 B+ 树能索引的行数是 `1170³ ≈ 16 亿`。

也就是说，**16 亿行数据，查一条只要 3 次磁盘读取**。这个数字是 B+ 树真正的竞争力：它不靠「树高很小」取胜，而靠「每一层塞得极满」。

## 为什么不选红黑树

红黑树也是有序的，查找也是 O(log n)，听起来够用。但把它放进磁盘就露馅了：

- 红黑树是**二叉**的，扇出只有 2，树高约为 `log₂(n)`；16 亿行就是 31 层。
- 每一层都可能是一次随机 IO，31 次 IO 和 3 次 IO 差了一个数量级。
- 红黑树节点小，一次磁盘读取只能拿到一个节点，剩下的空间浪费了。

所以 B+ 树的本质是：*把「树的高度」换成「页的宽度」*，让每次 IO 都尽量满载而归。

## 有序带来的三个白送的好处

回到最初的问题。有序结构除了「点查」，还顺手解决了三件事，而这三件事哈希表都做不了：

1. **范围查询**：`WHERE id BETWEEN 100 AND 200`，定位到 100 之后顺着叶子链表扫，不用回表重找。
2. **排序免单**：`ORDER BY id` 直接按索引顺序读出来，省掉一次外部排序。
3. **前缀匹配**：`LIKE 'abc%'` 能走索引，因为有序保证了「以 abc 开头的都挨在一起」。

### 叶子节点之间的链表

这是很多人背了但没用上的细节：B+ 树的**叶子节点之间是双向链表**，而且所有数据都在叶子层，非叶子层只存目录。这正是范围查询能「扫一段」的原因。

```sql
-- 覆盖索引：只查 id 和 name，不回表
EXPLAIN SELECT id, name FROM users
WHERE id BETWEEN 100 AND 200
ORDER BY id;

-- type=range  key=PRIMARY  Extra=Using index
-- 没有 Using filesort，说明排序被索引吃掉了
```

## 聚簇索引与回表

InnoDB 的主键索引是聚簇的：叶子节点直接存整行数据。二级索引则只存「索引列 + 主键」，所以查别的列要再回主键树找一次。

| 索引类型 | 叶子节点存什么 | 查非索引列 |
| --- | --- | --- |
| 主键（聚簇） | 整行数据 | 直接返回 |
| 二级索引 | 索引列 + 主键 | 回表一次 |
| 覆盖索引 | 查询需要的全部列 | 无需回表 |

> 回表不是「多查一次」，而是「多一次随机 IO」。所以慢查询优化里，覆盖索引的收益经常比加索引本身还大。

## 一个容易忽略的细节

B+ 树的页在磁盘上不是连续的。写入过程中页会分裂，逻辑相邻的页物理上可能很远。所以**范围扫描虽然是顺序遍历链表，但每一次跳页仍可能是一次随机 IO**。这也是为什么大范围扫描要比小范围慢得多——不是算法问题，是物理问题。

> **实践含义：** 分页查询 `LIMIT 100000, 20` 慢，本质是扫了十万行才丢掉；用「记住上一页最后一个 id」的游标分页可以绕开它。

## 小结

有序不是索引的「实现细节」，而是它存在的理由。哈希表能回答「这个值在不在」，只有有序结构能回答「这个范围内的有哪些、按什么顺序」。
